# LLM Wiki：让跨资料理解持续累积

Karpathy 提出的 LLM Wiki 模式，在原始资料与问答之间维护一层持续更新的知识文章。每次读新资料或回答问题，都可以修订已有理解；跨来源的连接、比较和分歧由此不必在下一次查询时全部重建。

## 从重复拼接到累积理解

The core idea 用一个常见场景引出问题：回答复杂问题可能需要综合多份文档，如果综合只存在于当次回答中，下次仍要重新查找、拼接。作者建议把综合结果写进持久 Wiki，并在新证据到来时更新。

这里保存的产物超出了逐篇摘要：同一实体的多源信息可以合并，同一主题的解释可以修订，新旧材料的冲突可以明确保留。其关键是让知识在多轮阅读之间累积，而不是只让原始文件越来越多。

## 三层结构为何分开

Architecture 分成 Raw sources、Wiki、Schema。原始资料保持不变，提供可回查的依据；Wiki 保存可更新的摘要、概念、比较与综合；Schema 规定页面与维护方式。

三层分开后，一篇新资料既可以产生单篇解读，也可以改动已有主题。来源保留原貌，综合允许改变，规则则随使用经验调整。作者在 Note 中强调，目录、工具和输出形式均可按领域选择，原文没有要求采用特定应用。

## 摄入、提问与检查如何共同更新知识

Operations 定义三种活动：

| 活动 | 对知识产生的作用 |
|---|---|
| Ingest | 阅读新来源，更新摘要、实体/概念、主题关系与冲突 |
| Query | 搜索相关页、引用回答，把有价值的分析或比较沉淀回来 |
| Lint | 查找矛盾、过时陈述、孤页、缺失关联和资料缺口 |

Indexing and logging 进一步区分内容目录与时间日志：前者回答“有什么知识”，后者回答“何时发生了什么变化”。两者都帮助导航，但不代替知识正文。

这一思路形成了 [持久知识层](../../知识库/概念/持久知识层.md) 与 [知识维护](../../知识库/综合/知识维护闭环.md) 的组织基础。具体科研引用仍需另行约束，见 [证据与适用范围](../../知识库/概念/证据与适用范围.md)。

## 适用边界

原文是设计模式与作者经验，未给出受控的检索或推荐实验。“维护成本近乎为零”、约百份来源与数百页的使用描述不能视作普遍性能保证。它最直接的启发是把已有理解保存下来；准确性和维护质量仍需回查与修订。
