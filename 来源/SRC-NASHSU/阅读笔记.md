# llm_wiki：缓存、页面合并与写入协调

nashsu/llm_wiki 将来源摄入、页面合并、检索与审核放入桌面应用。对轻量知识库最值得借鉴的部分，是缓存何时失效、多个来源怎样共享一页，以及并行准备如何与写入顺序协调。以下基于固定版本的定向静态阅读。

## 来源未变，输出缺失仍需重新摄入

[ingest-cache.ts::checkIngestCache](https://github.com/nashsu/llm_wiki/blob/e08cfce65aad8b76b13546a081c1a8d4422b70c3/src/lib/ingest-cache.ts#L67) 先比较来源内容 SHA256，再逐一检查历史输出是否存在。任何输出缺失或存在性检查失败，都返回缓存未命中。

源码注释解释了后一项检查的原因：过去直接信任缓存文件列表，可能在界面产生指向缺失页面的条目。可复用的经验是，缓存既要记录输入身份，也要确认处理结果仍可用。

CacheEntry 的字段为 `hash`、`timestamp`、`filesWritten`，这一结构没有编码完整处理协议。它不能单独说明解析规则或阅读要求改变时如何失效；也不能据此断言整个应用没有其他机制。相关取舍见 [增量摄入与失效传播](../../知识库/概念/增量摄入与失效传播.md)。

## 数组并集与正文合并解决不同问题

[page-merge.ts::mergePageContent](https://github.com/nashsu/llm_wiki/blob/e08cfce65aad8b76b13546a081c1a8d4422b70c3/src/lib/page-merge.ts) 的已读部分包含几类保护：

| 处理 | 作用 | 边界 |
|---|---|---|
| sources/tags/related 数组并集 | 保留来源和关联列表 | 来源名保留不等于正文贡献保留 |
| 锁定 type/title/created | 稳定页面身份 | 不能检查具体技术陈述 |
| 调用模型合并不同正文 | 尝试形成统一解释 | 仍可能失败或合并不完整 |
| 正文长度检查与备份钩子 | 拒绝明显压缩、提供恢复机会 | 长度不能证明语义完整，备份也不等于已经恢复 |

读到的模型失败与检查拒绝分支，会回退为新正文加数组并集。因此，即使全部来源仍在列表里，旧来源提供的某个前提也可能消失。这是 [逐项证据引用](../../知识库/概念/证据与适用范围.md) 仍有必要的一个工程例子，并非对全部合并路径的完整审计。

## 并行准备与顺序写入

`ingest-commit-coordinator.ts::reserve` 允许准备工作并行，但按预留顺序进入提交，并在 finally 中释放。它处理的是写入协调，不能替代正文冲突判断。轻量仓库可以先约定唯一整合者串行写入；是否需要程序队列，应由实际并发需求决定。

## 结构检查与检索的可见范围

`lint-structural-core.ts::computeStructuralLint` 使用入链计数、断链/无出链检查与候选关联启发。这些规则能帮助定位问题，无法证明研究结论正确。

`search.ts::searchWiki` 是调用共享 Rust 后端 `search_project` 的前端封装；已读文件不包含完整搜索实现，不能由此推断全部排序策略或检索性能。README 描述了桌面交互、可选向量检索和异步审核等功能，这些文档声明不等同于实际运行验收。

这些机制与来源组织、语义判断的关系见 [知识维护](../../知识库/综合/知识维护闭环.md)。
