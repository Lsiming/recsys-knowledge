# OneRec-V2：把目标物品解码成本压到极低，再用真实反馈做生成式对齐

短视频推荐若把历史编码、候选召回、粗排和精排全部拆开，系统可以复用候选表示，却也会在阶段之间传递目标不一致和候选遗漏。OneRec-V2把问题改成：给定按时间排列的曝光历史，直接生成下一个目标物品的离散语义码，再把生成结果接入线上反馈闭环。它的核心不是“删掉上下文”或“只用一个Transformer”，而是用轻量的上下文处理器、交叉注意力与因果解码器，把绝大多数计算留给历史表示复用；后训练阶段再用真实用户反馈构造组内相对优势，以GBPO约束概率更新。

固定阅读版本为[arXiv:2508.20900v4](https://arxiv.org/abs/2508.20900v4)（2025-10-28）。本文使用v4正文、图1–12、表1–9和附录A–D；参考文献未逐篇核实，未读作者实现，也未运行模型。译文范围、原件哈希与PDF验收记录在来源卡；中文PDF为工作译本，图内英文、附录和参考文献保留。

## 从整段会话生成改为目标物品级训练

OneRec-V2的监督单位是一个目标物品的三个SID。对每个时间点，输入是历史上下文与目标前两个码$[s_1,s_2]$，模型预测第三个码$s_3$；训练样本按曝光时间组织，只对最新目标物品计算损失。更早的曝光仍作为上下文，因而会通过历史表示影响最新目标的梯度，不能把灰色历史理解成“没有训练作用”。这与库内[OneRec-V1](../SRC-ONEREC/阅读笔记.md)的“生成一次请求的完整列表”不同：V2先把目标解码开销压小，再在服务侧逐目标生成。

物品由三个离散语义码表示。训练损失对三个Token平均，v1的相关表述是求和；跨版本比较loss前必须先核对归约方式。V2预训练使用最长512的上下文，线上设置扩展到3000。表1按1B参数估算，编码器—解码器在$N=512$时目标解码约8.1 GFLOPs、占总计算2.34%，$N=3000$时占0.41%；朴素1B纯解码器的目标解码约18 GFLOPs，但上下文项仍随$N$增长。表1是计算估算，不是端到端延迟或吞吐实测。

## 上下文处理器与惰性解码器

模型保留cross-attention和causal self-attention，block顺序为“cross-attention → causal self-attention → FFN”，深层FFN可以替换为MoE。它移除了传统编码器—解码器中的深编码器，并把上下文的K/V投影共享到较少的组；这使得目标生成可以复用历史侧状态，但不等于没有上下文，也不等于上下文读取成本为零。

Context Processor把历史侧表示切成共享的键值组。论文给出的维度关系为

$$d_{context}=S_{kv}L_{kv}G_{kv}d_{head},$$

其中默认$L_{kv}=1$、$S_{kv}=1$，并令$V=K$。$G_{kv}$控制键值组数；GQA再让多个查询头共享键值。表4将$G_{kv}$从14降到1时，KV规模从94M降到7M，GFLOPs仅由18.89降到18.62，收敛损失仍约3.27。因此KV显存缩减与总计算缩减不是同一个指标。图11的左/右图标题和图例分别呈现key-value sharing与grouped query attention，图注与图内命名有可能互换，已作为待审核事实保留。

层映射使用$\lfloor lL_{kv}/N_{layer}\rfloor$式的共享索引。按论文正文直接解释时，层号的起点和最后一层是否越界没有充分说明；未查代码，不补造实现修复。附录B把同一用户的5个物品共享上下文后按$N/5$摊销编码器项，但对attention score使用$(N/5)^2$与真正共享全历史后再摊销的$N^2/5$并不相同，且忽略了部分注意力项。这是近似估算，不能据此断言服务成本完全不随历史长度或目标数增长。

## 规模实验支持什么

在固定数据量下，0.1B到8B的稠密模型loss从3.57降到3.19；4B总参数、0.5B激活的MoE模型loss约3.22。v4新增固定数据下的拟合：

$$\hat L(N)=3.13+\frac{3660}{N^{0.489}}.$$

这里$N$是实际参数数（例如$10^8$），不是以十亿为单位的数；拟合只有7个规模点，没有不确定度、独立held-out数据或算力最优实验，不能称为完整Chinchilla定律验证，也不能作通用外推。附录B中的“encoder-decoder比纯解码器省多少”同样是计算模型，不是所有服务配置的实测优势。

## 从奖励模型转向真实反馈的GBPO

V2保留流式SFT，但后训练直接使用用户反馈。视频长度先按$F(d)=\lfloor\log_\beta(d+\epsilon)\rfloor$分桶；对用户$u$在同一长度桶的观看分位定义为

$$q_i=\frac{|\{p_j:p_j\le p_i\}|}{|P_{u,b}|}.$$

每个batch按$q$降序取前25%作正优势候选。负反馈为$-1$；高分位且没有负反馈的样本为$+1$，其余样本过滤。论文没有充分说明空桶、短历史、并列分位和统计截止时间，不能把该规则理解为已校准的因果价值。

对非零优势样本，目标写为

$$J=-\mathbb E\left[\frac{p}{b}A\right],$$

正优势使用$b=\max(p_{old},\operatorname{sg}(p))$，负优势使用$b=\max(p_{old},1-\operatorname{sg}(p))$。分母停梯度；数值上$p/\operatorname{sg}(p)=1$不表示对模型参数的导数为零。作者所说的“全样本”是筛选后非零优势样本不再按ratio截断梯度，并非所有曝光都训练。

当$A=+1$或$-1$时，概率坐标下的系数分别受$1/p$或$1/(1-p)$影响。它可以解释GBPO相对传统比率裁剪的梯度稳定性，但不能推出全参数梯度全局有界或数学收敛。低$p$负例的$1/p$放大还要结合softmax从logit到概率的导数，不能简单写成“低概率必然梯度爆炸”。

对OneRec生成的曝光样本，系统记录生成时的$p_{old}$。传统级联样本没有相同的生成概率，论文令$p_{old}=\operatorname{sg}(p_{current})$，使ratio数值为1。这是一个训练基线约定，不是真实propensity，也不能声称整个训练严格on-policy或已经消除曝光偏差。

## 线上证据与生态代价

表6把传统样本与OneRec生成样本放在近似相同的总样本量下比较；加入生成样本后，多数点赞、关注、评论、收藏和转发指标转正，但watch time并非所有场景都更高。表7比较奖励模型、用户反馈信号和混合方案：用户反馈在停留和观看指标上更强，混合方案在Kuaishou Lite的watch time为-0.398%；Lite Follow的数值是奖励模型12.242%高于混合11.705%，表中加粗与数值不一致，应以原数值为准。

正文表8是5%实验组、为期一周、1B模型、上下文3000、beam 512、L20、36ms、MFU 62%的线上结果；相对OneRec-V1，App停留时长在两个平台分别提升0.467%和0.741%，LT7分别提升0.069%和0.034%。4亿DAU是平台规模，不是实验人数；论文没有给出P95/QPS、批次、置信区间和完整随机化细节。不能把不同配置的表6–9数字拼成一次实验，也不能把这些离线或线上相对提升解释为长期因果收益。

附录D进一步说明，5%实验组中只有25%的degraded traffic实际调用OneRec；另有1%组关闭缓存，组内才是全请求调用。关闭缓存时，冷启动视频观看下降44.704%/36.730%，cluster density上升11.692%/7.933%，Lite forward上升30.957%，超过正文“9.6–29.2%”的文字范围。该结果说明生成接口会改变生态分布与服务成本，不能只看局部互动指标。

## 与现有知识对象的关系

- [目标感知排序怎样复用历史计算](../../知识库/问题/目标感知排序怎样复用历史计算.md)讨论HSTU/M-FALCON如何在候选互不可见时共享历史KV。OneRec-V2的上下文KV共享服务于目标码生成；它仍让生成目标按前缀依赖，不能把候选隔离式打分等同于列表生成。
- [生成式推荐怎样从似然训练走向偏好对齐](../../知识库/问题/生成式推荐怎样从似然训练走向偏好对齐.md)中的OneRec-V1是arXiv:2502.18965的DPO/IPA整列表版本。V2参考文献中的“V1”实际指OneRec Technical Report arXiv:2506.13695，使用ECPO；不能把两篇版本静默合并，也不能把V2的GBPO改写成V1的DPO。
- [生成式推荐怎样选择输出对象与评估目标](../../知识库/问题/生成式推荐怎样选择输出对象与评估目标.md)可用来区分V2的目标物品码、OneRec-V1的完整会话列表、TokenRec的连续表示和OneSug的文本查询。输出对象改变后，合法性、覆盖、重复、延迟和业务指标都要分别验收。
- [长历史怎样在候选条件下压缩计算](../../知识库/问题/长历史怎样在候选条件下压缩计算.md)中的SIM是先检索相关历史再精细建模；V2是保留上下文并减少投影/解码开销，二者都不能用一个“长历史压缩”标签替代。

OneRec-V2新增的可复用问题是“**生成推荐怎样把计算集中到目标解码**”：先按生成单位拆分上下文成本、目标成本、KV存储和多步解码，再判断共享是否改变任务语义；随后把真实反馈的筛选、优势定义、概率基线和线上生态指标分开核验。
