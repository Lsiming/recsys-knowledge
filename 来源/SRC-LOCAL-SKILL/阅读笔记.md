# llm-wiki v4：把新增内容合并进已有知识

本地 llm-wiki skill 将知识维护拆成检索、更新、合并与检查。最有用的约束是先找到已有的知识对象，再把新内容合进去，并同步检索入口；这样可以减少重复页面和互相失联的笔记。

## 先定位，再更新

SKILL.md 的 First Load / Fast Retrieval 要求从索引与上下文路由定位最小相关页面集合，具体问题再用关键词和别名检索。Before Updating / Update Chain 进一步要求，创建页面前先搜索，同一对象优先更新已有页。

配套 SCHEMA 的 Page Thresholds 将新页限制在反复出现、来源核心或稳定任务入口等情形。其作用是控制碎片化：一次性细节可以留在单篇笔记，重复使用的概念再获得独立正文。

## 正文与检索入口一起变化

Update Chain 把正文、更新时间、相关链接、索引、路由和变更日志视为同一轮维护。如果只修改文章而不更新入口，新理解虽然存在，却可能无法在后续查询中被找到。

脚本还需要说明、配置及语义入口，避免读者只能看到一段脱离背景的代码。这些是维护约定；原文并未因此提供自动事务、并发锁或语义正确性保证。

## 冲突保留条件，不直接覆盖

Conflict Merge 要求比较日期、来源权威性、适用范围和指标定义。两份资料若条件不同，可以保留各自结论；新资料确实替代旧结论时，应保留简短的变更说明；无法判定时明确争议。

这套约定解释了为什么合并不能退化为“用新正文替换旧正文”。需要保留的通常正是那些容易在摘要中丢失的条件和限制，详见 [证据与适用范围](../../知识库/概念/证据与适用范围.md) 与 [增量摄入](../../知识库/概念/增量摄入与失效传播.md)。

## 检查与长期记忆

lint-policy 覆盖链接、索引、字段、孤页、长页和冲突。结构问题可以由程序定位，是否正确理解资料仍需阅读判断。Auto-Sync 则将稳定决定、可复用方法和已确认发现沉淀到知识页，排除临时进度、敏感信息和重复内容。

检索与维护的衔接见 [知识维护](../../知识库/综合/知识维护闭环.md)，长期积累的作用见 [持久知识层](../../知识库/概念/持久知识层.md)。本项目采用这些原则，具体目录、链接数量和 Git 方式由本项目规则决定，未迁入参考中的金融业务目录或远端同步操作。
