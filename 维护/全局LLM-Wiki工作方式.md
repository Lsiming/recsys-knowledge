# 全局 llm-wiki 的工作方式

全局 `llm-wiki` v4.0.0 把团队的 Markdown 知识页、检索入口、维护规则和同步脚本放在同一个 Git 仓库。安装位置由 `~/.llm-wiki-path` 指向。Agent 根据任务路由检索、阅读和判断证据，把可复用的结论合并进已有知识，同时更新检索入口。同步脚本辅助收集候选，获授权的 Git 推送把已提交的改动共享给团队。

## 文件各自承担什么

| 目录或文件 | 实际用途 |
| --- | --- |
| `SKILL.md`、`AGENTS.md`、`SCHEMA.md` | 声明何时启用 skill、怎么读写仓库，以及页面命名、元数据、标签和建页条件。`GUIDELINE.md` 提供详细说明，按需读取。 |
| `index.md`、`_meta/context-packs.md`、`_meta/alias-registry.md` | `index.md` 按类列页面和一句话摘要。上下文包按任务列触发词、核心页、扩展页与阅读顺序。别名表登记同义叫法和容易写错的链接目标。 |
| `concepts/`、`data/`、`features/`、`samples/`、`models/`、`pipelines/`、`infra/`、`operations/` | 分别保存概念、数据与公共 SQL、特征、样本、模型、流程、基础设施和运维知识。页面用 `[[wikilinks]]` 跨目录连接。 |
| `raw/`、`scripts/`、`templates/` | 分别保存最小可审计证据、可复用代码的归档副本和页面模板。`scripts/README.md` 提供脚本入口，`scripts/CONFIG.md` 解释复用时要确认的路径、表、日期等环境参数。 |
| `log.md`、`_meta/update-policy.md`、`_meta/lint-policy.md` | `log.md` 追加维护动作、来源和变更文件；两份策略分别定义写入闭环和结构审计。 |
| `install.sh`、`adapters/`、`sync/` | 安装器定位仓库并配置各客户端入口。适配文档描述触发方式。同步脚本负责找候选或执行 Git 命令。 |

## 查询先定位，再读正文

1. 明确任务是纯查询、资料摄入、脚本归档还是结构审计。纯查询先读 `AGENTS.md`、`index.md` 和 `_meta/context-packs.md`。近期变化可能影响答案时，再看最近的 `log.md`。写入要读 `SCHEMA.md` 和更新策略，结构审计也要读 `SCHEMA.md`，再按 lint 策略检查。
2. 选最贴近任务的上下文包，按顺序读核心页。用 `rg` 搜任务名称、术语、别名和正文，证据不足时才读扩展页或沿链接回查来源。要复用脚本时，先读对应知识页以理解输入输出和适用条件，再打开归档脚本和 `scripts/CONFIG.md`。
3. 回答时给出知识页、证据入口和适用条件。已有记录、Agent 推断和仍待确认的部分分别说明。只有得到新解释、纠错或可靠结论时才进入写入流程。

例如，问“同一个客户怎样关联多笔事件并做时间窗口”时，先选数据分析与样本构建包，找到 ID 关联和时间窗口核心页。然后按关联键、时间字段和命名别名查正文，再查看实际 SQL 的过滤条件与去重规则。索引能定位主题，`rg` 能查到尚未进导航的正文，证据回查决定结果能否用于当前场景。

## 从新材料到可复用知识

### 先判断沉淀对象和证据

| 新得到的内容 | 什么时候写 | 落在哪 |
| --- | --- | --- |
| 决策及理由 | 决策已形成，理由和适用条件清楚 | `concepts/` 或已有专题页 |
| SQL、代码或数据口径 | 已确认可用，能说明输入、约束和输出 | `scripts/` 加可发现的语义页，公共数据口径进入 `data/` 或 `samples/` |
| 数据探查、模型和特征结论 | 已有实际验证，能说清样本、指标和条件 | `data/`、`features/` 或 `models/` |
| 排障方法 | 修复已经确认，复现条件和检查方式可说明 | 对应业务页及 `operations/troubleshooting.md` |

临时进展、一次性日志、个人或敏感信息、与已有知识等价的内容跳过。摄入报告或项目资料时，`raw/` 优先保存直接支撑结论的方案、报告或小型汇总。归档说明记录来源仓库、提交或时间范围、作者、纳入和排除范围及恢复入口。只有图片承载无法用表格或文字保留的证据时才归档图片。删减副本的附件后要修正引用、标明裁剪范围，完整产物留在上游或制品库。

### 合并正文和检索入口

1. 写入前核对 Git 状态和差异。全局 skill 的写入流程要求先与远端基线对齐，遇到未提交改动或冲突时先保留现有工作，再处理同步。读 `SCHEMA.md`，搜索索引、上下文包、别名及正文，优先更新同一对象的已有页。概念在至少两个来源出现、是某个来源或任务的核心，或可作为稳定任务入口时，可以新建页。一次性提及放在已有正文或来源材料里。
2. 更新正文、`updated`、来源和适用条件。新语义页用小写连字符文件名，填写 `title`、`created`、`updated`、`type`、`tags`、`sources`，标签从约定词表选择，并给至少两个有意义的 `[[wikilinks]]`。超过约 200 行时考虑拆页或补 Agent 摘要；整页内容已被替代时按契约归档并修入口。
3. 页面新增、重命名、归档或内容实质变化时检查 `index.md`。常见任务的入口或阅读顺序变化时调上下文包，出现新叫法或反复断链时调别名表。归档脚本或 SQL 时，同轮补 `scripts/README.md`、语义页 `## 脚本归档` 和已有语义页的检索入口，必要时解释 `scripts/CONFIG.md` 中的环境参数。每次维护都补 `log.md`。
4. 收尾读 `git diff --name-status` 和正文 diff。由每个改动反查所需的索引、路由、归档入口或日志，并用原任务关键词和别名走一遍检索路径。更新链把这些动作视作同一轮工作，多文件协调由维护者完成。

### 用证据决定覆盖、并存或待核实

先把旧结论与新结论的来源版本、日期、权威性、适用对象、环境和指标定义摆在一起。能确认同一口径已经升级时，更正正文并保留简短的变更理由。两个口径各自成立时，保留两者并写清条件。证据不足以作出判断时，在 `contradictions:` 或正文记录争议，也可以用 `confidence: low` 或 `contested: true` 标明复核需要。遇到 Git 文件冲突，先合并实际文字，再重新核对含义和适用条件。

以一个假设场景为例。旧分析按事件日统计活跃用户，新报告按入库日统计收到过事件的用户，两者都写作“当日活跃用户数”。回查定义、日期过滤和去重键后，在原有数据口径页分别写“业务活跃”和“数据到达”，并链接归档 SQL。若新报告没交代时区或去重维度，就把缺口留在该段，暂缓合并成一条通用指标定义。更新索引摘要和日志后，用旧术语“活跃用户”与新术语“入库日”重查，验证两种问法都能回到口径页。

## 自动同步从触发走到哪里

### 客户端怎样发起

| 入口 | 安装器或规范里的实际行为 |
| --- | --- |
| Claude Code | 写入全局 Wiki 指引，复制 `SKILL.md`，注册 `Stop` hook。hook 追加时间和工作目录，只保留最近 100 行。会话内是否发现可复用结论、是否回写，由 Agent 判断。 |
| Codex | 安装器生成 `~/codex-wiki.md`，已有 `~/AGENTS.md` 时加引用。该说明要求在会话结束判断是否沉淀，也可由用户明确触发。这条安装路径没有注册结束同步程序。 |
| OpenClaw | 安装器把核心文件和目录软链到客户端的 skill 目录。适配说明把 HEARTBEAT 作为提醒 Agent 检查记忆的入口，依赖客户端实际送达该事件。 |
| 任务完成或显式请求 | 稳定决策、验证过的发现或用户说“sync wiki”等都会进入候选判断。写入和推送仍取决于当前任务的授权。 |

安装本身也有写入行为。`install.sh` 会克隆或尝试更新 Wiki、写路径标记、注册客户端，并在 `memo/` 登记 Git 身份、工具、机器和安装信息后尝试提交和推送。阅读或审计现有安装只需读取路径标记指向的仓库和相关脚本。

### 从记忆到提交

`sync/memory-to-wiki.sh` 接受 `--memory-dir`、`--wiki-dir` 和 `--dry-run`。未显式给目录时，Wiki 读路径标记，记忆目录只尝试默认的 `~/workplace/memory`。候选包括 `learnings/LEARNINGS.md` 中 `## ` 开头且标题行没有 `synced` 的条目、今天和昨天的日志，以及记忆目录上一级的 `MEMORY.md`。对文件路径型候选，脚本用正则提取最多十个英文或下划线术语，再用 `rg` 数命中文件。`LEARNINGS.md` 的候选以标题列出，回查正文由 Agent 完成。两种模式都只打印候选和提示。筛选、去重、合并页面及成功后标记已同步由 Agent 执行。

有授权且使用 `sync/git-push.sh` 时，脚本先 `git pull --rebase origin main`，失败则试普通 `git pull origin main`，再次失败就退出并要求手动解决。随后以工作区和暂存区 diff 判断是否有变化，再执行 `git add -A`、提交和推送。只有未跟踪文件，或只有已提交待推内容时，两个 diff 都为空，脚本会提前退出。进入暂存步骤时，`git add -A` 会纳入整个工作区的改动，脚本自身没有知识审计、任务归属或敏感信息过滤。是否能发布还取决于 Git 状态、权限和服务端设置。

## 门禁能证明什么

| 检查 | 核对对象 | 当前实现与边界 |
| --- | --- | --- |
| 结构 lint | 检查真实 Wikilink、索引覆盖、元数据、标签、孤页、超长页、过时路由和别名，并列出低置信度和争议。默认检查八个语义目录，排除模板、归档脚本、根操作文件和示例链接。 | 当前核对版本提供了 lint 清单。未找到专用执行入口或把它接到推送脚本、仓库级 hook 或 CI 的配置。远端服务端门禁未核验。 |
| diff 与可发现性 | 审核者能看到正文、入口与日志是否按需联动，是否混入别人的修改，旧结论的条件是否被删掉。 | 改动范围清楚仍需读实际证据。文件合并成功也需要复查处理后的表述。 |
| 语义与证据 | 对关键数字、表字段、指标口径或代码行为回到实际来源核对。实验观察、分析推断和未解决疑问可以各自追溯。 | 覆盖范围取决于实际读到的来源和复查过的运行条件。同步成功只证明 Git 接收了提交。 |

只读核查时，本机上下文包与别名表均有重复的 `updated` 字段。它们仍作为普通 Markdown 文件存放，可直接读到内容。这个例子说明元数据可以在没有自动执行门禁的情况下逐渐偏离约定。

## 当前推荐知识库采用的检查

本仓库沿用任务路由、先搜后写、正文差异审查和冲突保留。来源登记另保存固定版本与哈希。`plan` 用来源版本、笔记哈希、处理语义版本和整合记录找直接引用页，再提示一跳复核候选。`integrate` 校验当前来源版本、直接引用页覆盖和自查状态并记录收据。`wiki.py lint`、`index --check` 和 GitHub 工作流检查结构与索引，论文验收另做技术证据与读者路径自查。项目的写入和 Git 规则以 [维护工作流](工作流.md)、[知识契约](../SCHEMA.md) 和 [AGENTS](../AGENTS.md) 为准。
