# 增量摄入与失效传播

资料更新后，通常只有一部分知识需要重新审视。增量摄入需要识别两类变化：来源或处理依据是否改变，以及哪些既有结论受其影响。哈希能识别字节变化，但无法单独回答知识是否仍可复用。

## 缓存为什么还要检查输出

nashsu 固定版本的 `ingest-cache.ts::checkIngestCache` 同时检查来源内容 SHA256 与历史输出是否存在。若来源未变但某个输出已删除，它仍返回缓存未命中。源码注释说明，只信缓存列表曾产生指向缺失文件的“幽灵条目”。见 [源码范围与版本](../../来源/SRC-NASHSU/阅读笔记.md)。

该文件的 CacheEntry 包含 `hash`、`timestamp` 和 `filesWritten`，没有在这一结构中编码完整处理协议。这意味着，单看这一缓存结构，无法判断阅读要求改变后是否应重新处理；不能由此推断整个上游应用没有其他机制。

## 把处理依据也纳入失效判断

一种更完整的记录由四部分组成：

| 记录 | 变化时意味着什么 |
|---|---|
| 来源指纹 | 版本、实际阅读范围或原件发生变化 |
| 处理语义版本 | 提取范围、证据要求或合并语义发生实质变化 |
| 阅读笔记哈希 | 对来源的解释或阅读记录被修订 |
| 输出页面与来源绑定 | 原输出丢失、引用断开或仍使用旧版本 |

本仓库的 [wiki 工具](../../scripts/README.md) 使用这些记录生成增量计划，并检查来源状态、页面自查状态和新增引用页。处理语义版本显式维护：只有旧资料确需按新规则复核时才升版。修改目录排版、导航或普通工具结构，不应让所有已读论文重新排队。

这里有一个取舍：自动哈希全部规则和工具代码更敏感，却会把无关排版也当成重处理原因；显式语义版本减少无谓工作，但需要维护者判断规则变化是否影响旧知识。版本匹配只表示记录没有已知变化。

## 直接影响与关联影响

知识页将来源 ID 绑定到实际阅读版本。来源升级时，保留旧绑定，才能识别仍依赖旧证据的页面。直接引用页应逐条复核；一跳关联页只是候选，因为概念相关不等于结论受影响。

重新整合也不能只是替换指纹。本地 llm-wiki skill 的 Conflict Merge 要求比较日期、权威性、范围与指标。nashsu `page-merge.ts` 的已读失败分支则提示另一种风险：数组并集可以保留来源名，正文仍可能丢失旧贡献。合并时需要保留仍成立的条件，无法确认的补充留待核实。见 [规范笔记](../../来源/SRC-LOCAL-SKILL/阅读笔记.md)、[源码笔记](../../来源/SRC-NASHSU/阅读笔记.md)。

## 为什么不锁定整篇知识正文

同一问题页会不断接收其他论文的补充。若旧来源的收据锁定整个页面哈希，每次正常增补都会使所有旧来源失效。因此，当前收据记录输出身份与来源绑定，不锁定正文全文。

代价是正文误删可能逃过记录检查，需要通过 diff、原文核对与 Git 历史发现。原件快照也需要独立备份；哈希能发现损坏，不能恢复缺失内容。增量计划为空表示没有已知记录积压，结论是否成立仍由 [证据与适用范围](证据与适用范围.md) 判断；整体关系见 [知识维护](../综合/知识维护闭环.md)。
