# 查询理解与结构化表达

同一句查询可能同时表达对象、用途和限制。搜索后端要把它们转成可消费的信号；如果多个独立组件给出不一致的实体或意图，下游可能沿错误方向检索。这里的输入是查询及实际可用的上下文，输出是结构字段、任务结果或意图描述。输出怎样定义，要由业务和检索接口确定。

[LinkedIn固定v2摘要](https://arxiv.org/abs/2605.27441v2)将分散组件统一为SLM的Schema约束生成；Schema指输出必须遵循的字段与结构约定。[QP-OneModel固定v1摘要](https://arxiv.org/abs/2602.09901v1)将SNS搜索的异构子任务统一为序列生成，并把意图描述作为改写和排序的下游信号。两篇分别提示结构一致性与语义信号共享，不足以证明某种统一格式适用于所有搜索场景。

## 三个待研究问题

<a id="q-schema"></a>**多任务输出怎样保持结构和语义一致？** 结构合法只保证格式可解析，不能保证实体、意图和限制之间没有矛盾。后续需明确哪些任务共同生成、哪些依赖其他任务、未知或歧义如何表达，以及错误会在哪个下游环节放大。LinkedIn与QP-OneModel提供候选路线；用户原清单中的“五项功能”“9类任务”尚未用正文逐项核实。

<a id="q-domain"></a>**领域语言和业务定义怎样进入模型，并被下游正确使用？** QP-OneModel摘要强调SNS口语表达与开放域语料的差距、严格业务定义和多奖励对齐，还提出意图描述增强改写与排序。待比较的是结构字段与自由文本意图各自传递了什么，领域监督从哪里来，未见任务测试是否排除了训练模板或标签定义泄漏；不先假定意图描述必然提升所有下游。

<a id="q-teacher-judge"></a>**教师标注与代理评委怎样被独立验证？** LinkedIn摘要中的Query Illuminator同时负责自动标注/蒸馏和代理评价。可扩展的标签供给由此成为模块的一部分，但教师和评委共享偏好也可能使评价循环自洽。这是本库提出的验证问题，尚不是论文已证实的缺陷。精读要看独立人评、分歧样本、任务覆盖、跨域案例及成本协议。

## 与已有模块怎样衔接

[P5统一任务接口](../问题/如何用语言接口统一个性化推荐任务.md)可以帮助理解“多任务都写成序列预测”，[多任务共享](多任务学习与多目标决策.md)可帮助分析冲突与负迁移，但它们没有覆盖搜索字段的相互约束、SNS领域定义和意图描述的后端消费。理解产物如何转为检索请求见[查询改写与规划](查询改写与检索规划.md)，结果是否满足需求见[搜索相关性](搜索相关性判断与验证.md)。
