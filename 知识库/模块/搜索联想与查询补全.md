# 搜索联想与查询补全

联想发生在用户尚未完整表达需求时。输入是前缀及当时可用的上下文，输出是一组供用户选择的查询；它既帮助表达，也可能改变后续搜索方向。商品推荐输出物品，查询改写通常处理已提交需求，二者都不能替代前缀到建议查询这一接口。

[OneSug v1摘要](https://arxiv.org/abs/2506.06913v1)用prefix2query表征增强补足前缀语义与交互信息，以编码器—解码器统一生成，并采用行为加权的奖励排序。[LocalSUG v3摘要](https://arxiv.org/abs/2603.04946v3)强调城市偏好、偏好优化中的曝光偏差及在线时延，提出动态城市参考、beam驱动GRPO与加速。它增加了本地服务条件，但摘要并不能证明它是OneSug的直接改版。

## 三个待研究问题

<a id="q-prefix"></a>**信息不足的前缀怎样生成相关且有区分度的建议？** OneSug摘要通过语义和交互相关的查询增强前缀。后续需核实前缀歧义如何保留、增强信息如何取得、用户偏好如何参与，以及奖励是否过度集中在少数高交互查询。既有[用户兴趣](用户兴趣与序列建模.md)可以解释偏好来源，但尚无前缀条件下的意图与建议列表问题。

<a id="q-city"></a>**同一前缀怎样适应城市差异和本地供给变化？** LocalSUG摘要从词共现挖掘城市偏好候选，将它们作为动态prompt参考，而非融合进参数，意在适应门店开闭等变化。待核实的是城市候选的新鲜度、稀疏城市与新需求的覆盖、候选失效和本地无结果的判断。地理上下文进入模型不自动保证推荐的查询能搜到有效服务。

<a id="q-decoding"></a>**偏好训练怎样对齐实际生成列表和严格延迟？** LocalSUG摘要的beam驱动GRPO尝试对齐训练和推理解码，同时以质量感知beam加速与词表裁剪控制成本。后续要比较训练候选与在线beam的分布、裁剪漏失以及相关性/业务奖励冲突。摘要提及的偏好优化曝光偏差如何被缓解，不能仅从算法名称推出。OneSug的行为加权策略也需要在同一问题下对照监督来源与推理形式。

## 怎样评价建议查询

前缀匹配、建议本身的可读/相关、用户选择、选择后的检索有效性与业务转化属于不同节点。本库拟按前缀长度、长尾程度、城市与供给变化分层，并同时看覆盖、重复、无结果和整条链路时延；这些是待核实的评价轴，不是两篇均已报告的指标。点击最多的建议也可能受展示位置影响，需与[训练和曝光边界](训练目标与偏好对齐.md)一起审查。

查询被选择后再进入[改写与规划](查询改写与检索规划.md)；多路径生成与成本继续复用[解码模块](生成机制与约束解码.md)和[在线服务](在线服务、更新与计算效率.md)。阅读入口为[P42 OneSug](../阅读/候选论文.md#p42)、[P43 LocalSUG](../阅读/候选论文.md#p43)，固定版本及摘要范围见[搜索总图](../总览/搜索系统总图.md#版本与阅读边界)。
