# 搜索联想与查询补全

联想发生在用户尚未完整表达需求时。输入是前缀及当时可用的上下文，输出是一组供用户选择的查询；它既帮助表达，也可能改变后续搜索方向。商品推荐输出物品，查询改写通常处理已提交需求，二者都不能替代前缀到建议查询这一接口。

[OneSug v1精读](../../来源/SRC-ONESUG/阅读笔记.md)已核实前缀参考增强、文本生成和行为等级偏好机制，入口为[短前缀到查询建议问题](../问题/短前缀怎样生成相关且有排序能力的查询建议.md)。[LocalSUG v3摘要](https://arxiv.org/abs/2603.04946v3)强调城市偏好、偏好优化中的曝光偏差及在线时延，提出动态城市参考、beam驱动GRPO与加速。它增加了本地服务条件，但摘要并不能证明它是OneSug的直接改版。

## 前缀生成与两个延伸问题

<a id="q-prefix"></a>**信息不足的前缀怎样生成相关且有区分度的建议？** [OneSug的已读方案](../问题/短前缀怎样生成相关且有排序能力的查询建议.md)先以业务配对对齐BGE，混合共现查询表示，再用RQ-VAE桶取得参考；生成器输出文本，行为等级构成成对或多负例偏好。共现与反馈仍受旧曝光影响，完全无共现前缀的回退、奖励差稳定及公式梯度需进一步核实。既有[用户兴趣](用户兴趣与序列建模.md)提供历史表示背景。

<a id="q-city"></a>**同一前缀怎样适应城市差异和本地供给变化？** LocalSUG摘要从词共现挖掘城市偏好候选，将它们作为动态prompt参考，而非融合进参数，意在适应门店开闭等变化。待核实的是城市候选的新鲜度、稀疏城市与新需求的覆盖、候选失效和本地无结果的判断。地理上下文进入模型不自动保证推荐的查询能搜到有效服务。

<a id="q-decoding"></a>**偏好训练怎样对齐实际生成列表和严格延迟？** LocalSUG摘要的beam驱动GRPO尝试对齐训练和推理解码，同时以质量感知beam加速与词表裁剪控制成本。后续要比较训练候选与在线beam的分布、裁剪漏失以及相关性/业务奖励冲突。摘要提及的偏好优化曝光偏差如何被缓解，不能仅从算法名称推出。OneSug已经采用日志行为加权与beam32推理，但列表训练是多负例比较，不是整张建议列表的自回归生成；不能由损失名推出训练候选与beam分布已一致。

## 怎样评价建议查询

前缀匹配、建议本身的可读/相关、用户选择、选择后的检索有效性与业务转化属于不同节点。本库拟按前缀长度、长尾程度、城市与供给变化分层，并同时看覆盖、重复、无结果和整条链路时延；OneSug报告足额16条、查询/整页语义优质率及线上CTR、订单、收入；这些轴不全是两篇都已测量。它的full recall rate实际是足额返回率，不能当相关查询全集召回；具体证据与缺项见[问题页](../问题/短前缀怎样生成相关且有排序能力的查询建议.md#先问建议是否可用再看被选择与业务转化)。点击最多的建议也可能受展示位置影响，需与[训练和曝光边界](训练目标与偏好对齐.md)一起审查。

查询被选择后再进入[改写与规划](查询改写与检索规划.md)；多路径生成与成本继续复用[解码模块](生成机制与约束解码.md)和[在线服务](在线服务、更新与计算效率.md)。阅读入口为[P42 OneSug](../阅读/候选论文.md#p42)、[P43 LocalSUG](../阅读/候选论文.md#p43)，固定版本及摘要范围见[搜索总图](../总览/搜索系统总图.md#版本与阅读边界)。
