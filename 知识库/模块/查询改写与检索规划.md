# 查询改写与检索规划

用户描述需求的方式不一定等于物品被组织和索引的方式。改写要弥合这种差距；规划还要决定发出哪些请求，以及这些请求能否在真实后端上执行。输入是查询、已有理解及可访问的环境信息，输出是改写、互补查询组合或检索计划，后续仍由检索接口发现候选。

[BEQUE v3摘要](https://arxiv.org/abs/2311.03758v3)针对长尾查询因语义缺口而少召回的问题，通过多指令SFT、离线系统反馈与偏序对比学习对齐改写。[LEAPS v2摘要](https://arxiv.org/abs/2601.05513v2)针对自然语言、多约束需求，用互补扩展增加候选，再在下游验证相关性。[EASP v2摘要](https://arxiv.org/abs/2603.15262v2)进一步把检索快照交给规划器，诊断执行缺口；三者由不同位置连接语言与后端。

## 三个待研究问题

<a id="q-longtail"></a>**长尾查询怎样跨过语义缺口而保持原意？** BEQUE摘要将多个候选改写交给淘宝离线系统获得偏序，再以对比目标区分候选。后续需核实偏序评价的是召回、相关性还是复合业务目标，以及改写是否保留原查询关键要求。多召回一些商品和更完整地满足用户需求是不同评价对象；线上缓存的具体形态尚未由摘要确认。

<a id="q-constraints"></a>**复杂查询怎样扩展为互补请求，并保留多项约束？** LEAPS摘要给出逆向数据增强、后验知识SFT和多样性RL，目的在于形成互补扩展。待研究的是不同扩展各覆盖什么需求，候选并集增长是否只是放松约束，以及后验信息训练时可用、推理时不可用的边界。扩展后噪声由谁判断，连接[相关性验证](搜索相关性判断与验证.md#q-evidence)，不把候选变多直接当作质量提高。

<a id="q-environment"></a>**规划怎样感知实际供给与检索能力，并控制总时延？** EASP摘要提出轻量Retrieval Probe提供检索快照，教师合成执行验证过的计划，再以SFT和转化率RL训练规划器，线上按复杂度选择启用。快照能揭示什么、漏掉什么，库存和索引变化是否使计划失效，简单查询被错误分流的代价多大，都需正文证据。摘要里的工业亚秒预算是问题条件，不能代替具体延迟分位数实测。

## 与已有模块怎样衔接

[召回与检索](召回与检索.md)负责给定请求后发现候选；这里新增的是请求本身的构造与执行可行性。[训练与偏好对齐](训练目标与偏好对齐.md)继续承接SFT、对比学习和RL目标，但需核实改写与计划各自的奖励事件。[在线服务](在线服务、更新与计算效率.md)承接探针、路由和多请求成本；不要只统计语言模型生成耗时。

后续比较应固定原查询集、长尾/复杂度划分、后端索引与供给快照、请求和候选预算，分别看原意保持、有效覆盖、无结果、噪声、延迟和业务结果。这些是本库拟定的比较轴，尚未核实各篇的实际报告。阅读入口为[P40 BEQUE](../阅读/候选论文.md#p40)、[P47 EASP](../阅读/候选论文.md#p47)、[P51 LEAPS](../阅读/候选论文.md#p51)；版本和范围见[搜索总图](../总览/搜索系统总图.md#版本与阅读边界)。
