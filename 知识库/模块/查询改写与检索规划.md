# 查询改写与检索规划

用户描述需求的方式不一定等于物品被组织和索引的方式。改写要弥合这种差距；规划还要决定发出哪些请求，以及这些请求能否在真实后端上执行。输入是查询、已有理解及可访问的环境信息，输出是改写、互补查询组合或检索计划，后续仍由检索接口发现候选。

[BEQUE](../../来源/SRC-BEQUE/阅读笔记.md)针对长尾查询因语义缺口而少召回的问题，通过多指令SFT、离线系统反馈与偏序对比学习对齐改写。[LEAPS](../../来源/SRC-LEAPS/阅读笔记.md)针对自然语言、多约束需求，用互补扩展增加候选，再在下游验证相关性。[EASP](../../来源/SRC-EASP/阅读笔记.md)进一步把检索快照交给规划器，诊断执行缺口；三者由不同位置连接语言与后端。

## 三个待研究问题

<a id="q-longtail"></a>**长尾查询怎样跨过语义缺口而保持原意？** [可执行检索请求](../问题/复杂查询怎样生成可执行的检索请求.md#用离线试搜预生成改写)沿原查询与候选改写各走一次倒排召回，解释 BEQUE 如何用原意相关性、优质覆盖和场景外成交命中评价改写，再用偏序训练生成器。线上读取提前生成的改写，原词与改写结果取并集。扩展覆盖可能降低候选池的相关占比，原文表 5 的长尾分层保留了这个取舍。

<a id="q-constraints"></a>**复杂查询怎样扩展为互补请求，并保留多项约束？** [可执行检索请求](../问题/复杂查询怎样生成可执行的检索请求.md#对多项约束先扩大覆盖再复核原意)对照 LEAPS 的属性子集试搜、后验 SFT 和按有效覆盖奖励整组改写。覆盖扩张允许检索动作暂时省略部分属性，结果仍交给验证器按完整原查询核实，参见[相关性证据](搜索相关性判断与验证.md#q-evidence)。

<a id="q-environment"></a>**规划怎样感知实际供给与检索能力，并控制总时延？** [可执行检索请求](../问题/复杂查询怎样生成可执行的检索请求.md)比较一次探测、盲改写与多轮调用。EASP 的规划器先从轻量召回快照区分低召回和低精度，再选择保留、清洗、具体化或停止细化。GRPO 奖励是原查询相关性门控后的预测转化，线上路由仅为复杂查询启用探针。探针看见的是召回结果的局部快照，覆盖、时效与误路由影响仍需服务端验证。

## 与已有模块怎样衔接

[召回与检索](召回与检索.md)负责给定请求后发现候选；这里新增的是请求本身的构造与执行可行性。[训练与偏好对齐](训练目标与偏好对齐.md)继续承接SFT、对比学习和RL目标，但需核实改写与计划各自的奖励事件。[在线服务](在线服务、更新与计算效率.md)承接探针、路由和多请求成本；不要只统计语言模型生成耗时。

后续比较应固定原查询集、长尾/复杂度划分、后端索引与供给快照、请求和候选预算，分别看原意保持、有效覆盖、无结果、噪声、延迟和业务结果。三篇报告的指标与实验流量需逐项对齐。阅读入口为[P40 BEQUE](../阅读/候选论文.md#p40)、[P47 EASP](../阅读/候选论文.md#p47)、[P51 LEAPS](../阅读/候选论文.md#p51)；版本和范围见[搜索总图](../总览/搜索系统总图.md#版本与阅读边界)。
