# 搜索系统：查询、供给与相关性的问题地图

搜索多了一份用户主动表达的需求。系统既要从不完整的前缀帮助用户形成查询，也要把完整查询变成可执行的检索条件，判断真实供给能否满足它，再决定展示哪些结果。用户历史可以补充歧义，但不能未经判断就替换当前查询的显式要求。后一条是这里提出的分析原则，尚不是这9篇共同验证的结论。

现有[推荐系统主干](推荐系统总图.md)已经覆盖候选发现、兴趣建模、召排级联、训练、解码和评估。缺口在于：它没有独立描述“查询是什么意思”“怎样改写和执行”“前缀该补成什么”“结果是否满足查询”。这四种输出不同，不能都并入召回：理解输出意图或结构字段；改写与规划输出检索请求；联想输出给用户选择的查询；相关性判断输出查询—结果的关系或验证决定。

这九篇搜索论文均已对照固定版本全文。下图按查询在系统中的用途划分模块，同一篇论文可能同时涉及两个环节。读到具体方法时，可从[九篇论文与原文入口](#九篇搜索论文与原文入口)查阅各篇精读、适用条件和仍缺的证据。

## 查询进入系统后的几种职责

```mermaid
flowchart LR
    P[输入前缀] --> S[搜索联想与查询补全]
    S --> U[用户选择或继续输入]
    U --> Q[完整查询]
    Q --> I[查询理解与结构化表达]
    I --> E[查询改写与检索规划]
    C[当前供给与检索能力] --> E
    E --> R[召回与检索]
    R --> V[搜索相关性判断与验证]
    V --> K[排序与列表决策]
    Q --> G[查询条件下的端到端生成检索与排序]
    G --> K
```

这是按接口组织的学习图，不是9篇共同采用的架构。LEAPS横跨扩展与验证；OneSearch探索直接生成商品；联想输出还需要用户确认，不能把联想点击和商品点击当作同一事件。各条链路保留哪些过滤、回退与验证步骤，见下表的模块比较。

例如，同一句“附近适合带孩子的餐厅”，联想要决定向用户展示哪条补全，规划要构造可执行的检索请求，验证则要判断返回的每家餐厅是否满足约束。三处都使用查询文本，输出与验收单位各不相同。

## 共享模块还需要补的四个搜索问题

<a id="q-query-conditioned-generation"></a>**端到端生成怎样同时满足查询相关性与用户偏好？** OneSearch 让开放查询文本与其 SID 共同进入编码器，解码生成闭词表商品的 RQ-OPQ 编码。关键词和相关性校正用来训练表征，排序教师还将离线相关性分加进预测行为分。合法码、商品与查询相符、用户偏好各需不同证据。论文离线下单目标 HR@350 提高，MRR 略低；线上订单正向结果来自带奖励模型重排的实验组。[OneSearch 精读](../../来源/SRC-ONESEARCH/阅读笔记.md) · [短码检索比较](../问题/用语义短码直接检索物品.md#当前查询和商品编码承担不同的约束)

<a id="q-search-supervision"></a>**搜索监督究竟来自哪里，奖励优化了哪个事件？** BEQUE 用倒排试搜的相关比例、优质商品覆盖或场景外命中构造改写偏序，EASP 全文用原查询相关性门控的预测 CVR 对齐检索计划，OneSug全文以行为等级规则奖励构造偏好，LocalSUG 以训练束的目标命中、名次和格式等条件分配奖励，订单样本另加权。它们不能仅因都用了对齐就看成同一监督：人工相关性、改写后的检索结果、联想选择、商品交互和转化发生在不同节点。已有[训练与偏好对齐](../模块/训练目标与偏好对齐.md)与[数据和标签](../模块/数据、样本与标签.md)可复用，新增问题是如何连接这些节点、控制日志曝光和未来信息泄漏。OneSug 全文未充分披露奖励统计窗和订单成熟期，详见[偏好比较](../问题/生成式推荐怎样从似然训练走向偏好对齐.md)。

<a id="q-search-evaluation"></a>**查询理解正确、搜得到、搜得准和业务收益怎样分别验证？** 结构生成需要看字段与组合的一致性；改写需要看意图保真和查询条件下的有效覆盖；联想需要看前缀与城市条件下的可用性；相关性判断需要看人工标注和不同难度的错误。再接线上点击、转化、留存与成本。这里列出的是后续比较维度，不是各论文均已报告的指标。已有[评估模块](../模块/评估、偏差与因果收益.md)保留离线/因果边界，还需按长尾、复杂约束、城市与供给状态分层，各论文采用的请求分布、候选集和指标口径也要分别核对。

<a id="q-search-freshness"></a>**变化的供给怎样在延迟预算内进入决策？** [EASP](../../来源/SRC-EASP/阅读笔记.md) 在复杂路径取轻量检索快照，快路径直接进入搜索；[LocalSUG](../../来源/SRC-LOCALSUG/阅读笔记.md)每日更新城市共现参考，推理时用 QA-BS 和词表裁剪加速；LEAPS 通过插件接既有后端，分别披露扩展及逐商品验证的长度和服务配置。已有[在线服务](../模块/在线服务、更新与计算效率.md)可承接缓存、更新和推理成本，新增问题是快照时效、库存/门店变化、路由漏检与总链路预算。方案能否达到目标延迟，要读正文的请求分布、硬件、并发和回退配置，不能由“轻量”“低延迟”措辞推定。
