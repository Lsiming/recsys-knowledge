# 搜索系统：查询、供给与相关性的问题地图

搜索多了一份用户主动表达的需求。系统既要从不完整的前缀帮助用户形成查询，也要把完整查询变成可执行的检索条件，判断真实供给能否满足它，再决定展示哪些结果。用户历史可以补充歧义，但不能未经判断就替换当前查询的显式要求。后一条是这里提出的分析原则，尚不是这9篇共同验证的结论。

现有[推荐系统主干](推荐系统总图.md)已经覆盖候选发现、兴趣建模、召排级联、训练、解码和评估。缺口在于：它没有独立描述“查询是什么意思”“怎样改写和执行”“前缀该补成什么”“结果是否满足查询”。这四种输出不同，不能都并入召回：理解输出意图或结构字段；改写与规划输出检索请求；联想输出给用户选择的查询；相关性判断输出查询—结果的关系或验证决定。

本轮依据2026-10-26取得的9篇固定版本元信息与摘要建立学习框架。下面对论文的描述限定为作者摘要所述，模块边界与待研究问题是本库分析；未读正文、未翻译、未核验实现和实验协议，不据此登记已精读方案。正式题名和版本见文末，原用户清单仍可从[候选表](../阅读/候选论文.md#用户补充的生成式搜推论文)回查。

## 查询进入系统后的几种职责

```mermaid
flowchart LR
    P[输入前缀] --> S[搜索联想与查询补全]
    S --> U[用户选择或继续输入]
    U --> Q[完整查询]
    Q --> I[查询理解与结构化表达]
    I --> E[查询改写与检索规划]
    C[当前供给与检索能力] --> E
    E --> R[召回与检索]
    R --> V[搜索相关性判断与验证]
    V --> K[排序与列表决策]
    Q --> G[查询条件下的端到端生成检索与排序]
    G --> K
```

这是按接口组织的学习图，不是9篇共同采用的架构。LEAPS横跨扩展与验证；OneSearch探索直接生成商品；联想输出还需要用户确认，不能把联想点击和商品点击当作同一事件。过滤、回退和验证是否仍存在，后续逐篇读实际链路。

## 共享模块还需要补的四个搜索问题

<a id="q-query-conditioned-generation"></a>**端到端生成怎样同时满足查询相关性与用户偏好？** [OneSearch v5摘要](https://arxiv.org/abs/2509.03236v5)提出关键词增强的层次量化、多个视角的用户行为注入及偏好奖励系统。已有[语义码检索](../问题/用语义短码直接检索物品.md)讲物品表示与历史到物品生成，[级联模块](../模块/粗排与级联衔接.md)讲召排统一；尚缺当前查询、区分性商品属性和用户偏好之间的约束关系。后续要问：码的可映射性和商品满足查询分别由什么保证，奖励是否会牺牲相关性，过滤和回退还保留哪些阶段。继续复用表征、召回与级联模块，不另建“生成式召排”重复模块。

<a id="q-search-supervision"></a>**搜索监督究竟来自哪里，奖励优化了哪个事件？** BEQUE摘要用离线系统给改写排序，EASP摘要用转化率对齐规划，OneSug摘要给行为赋权，LocalSUG摘要将相关性与业务奖励结合。它们不能仅因都用了对齐就看成同一监督：人工相关性、改写后的检索结果、联想选择、商品交互和转化发生在不同节点。已有[训练与偏好对齐](../模块/训练目标与偏好对齐.md)与[数据和标签](../模块/数据、样本与标签.md)可复用，新增问题是如何连接这些节点、控制日志曝光和未来信息泄漏；摘要不能给出完整归因窗口与采样协议。

<a id="q-search-evaluation"></a>**查询理解正确、搜得到、搜得准和业务收益怎样分别验证？** 结构生成需要看字段与组合的一致性；改写需要看意图保真和查询条件下的有效覆盖；联想需要看前缀与城市条件下的可用性；相关性判断需要看人工标注和不同难度的错误。再接线上点击、转化、留存与成本。这里列出的是后续比较维度，不是各论文均已报告的指标。已有[评估模块](../模块/评估、偏差与因果收益.md)保留离线/因果边界，还需按长尾、复杂约束、城市与供给状态分层，不能跨论文摘要数字排名。

<a id="q-search-freshness"></a>**变化的供给怎样在延迟预算内进入决策？** EASP摘要给规划器检索快照并按复杂度选择启用；LocalSUG摘要将城市候选动态注入prompt而非写入参数，并使用解码加速；LEAPS摘要通过插件接既有后端。已有[在线服务](../模块/在线服务、更新与计算效率.md)可承接缓存、更新和推理成本，新增问题是快照时效、库存/门店变化、路由漏检与总链路预算。方案能否达到目标延迟，要读正文的请求分布、硬件、并发和回退配置，不能由“轻量”“低延迟”措辞推定。

这些摘要描述了不同的改造位置。BEQUE偏向用系统反馈优化改写；EASP将供给与执行能力显式交给规划器；LEAPS把扩大候选和验证收敛分在前后两端。三者可围绕“改写能否执行并满足意图”比较，但当前还没有同任务、同预算、同数据的证据。OneSug与LocalSUG共有前缀到查询接口，城市适配是后者摘要强调的额外条件；“特化版”只能作为任务类比，不能当作已核实谱系。
