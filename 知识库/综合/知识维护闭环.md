# 知识如何通过摄入、问答和检查生长

知识库的价值来自持续修订的理解。一篇新论文可以补充解法，一个问题可以暴露比较缺口，一次检查可以发现旧结论遗漏的条件。三种活动最终都应改进同一组问题文章，让下一次学习有更完整的起点。

## 三种增量各自带来什么

| 入口 | 典型增量 | 写入已有知识的方式 |
|---|---|---|
| 摄入资料 | 新机制、新证据、反例 | 补充或更正相关概念与方案比较 |
| 回答问题 | 跨资料连接、条件解释、推理缺口 | 把可复用解释合并到相应正文 |
| 检查知识 | 过时结论、条件遗漏、断开的依据 | 修正已确认的问题，保留尚待核实的分歧 |

Karpathy 的 Operations 将它们概括为 Ingest / Query / Lint，并强调有价值的回答可以沉淀回 Wiki。见 [原文定位](../../来源/SRC-KARPATHY/阅读笔记.md)。回答本身不会产生新的实验依据；由已有材料得出的解释仍是综合或推断。

## 用问题连接多篇论文

论文精读与问题文章采用不同叙述顺序。精读沿一项工作的动机、结构、训练推理和实验展开；问题文章把不同工作的解法放在一起，解释各自改变了哪个环节、依赖什么条件、带来什么代价。

学习路径因此可以组织为“模块 → 问题 → 解法 → 论文”。新论文到来时，先理解具体机制，再把可复用部分合并到相关问题；读者既能快速查看解法谱系，也能回到单篇论文追究细节。没有已读对照时先写清一种方案，待新证据出现后再扩展比较。

这一组织是本仓库根据论文学习需求作出的选择，三份参考并未规定推荐问题如何分类。关键在于一份主要正文承担一个稳定知识对象，避免论文摘要与问题页大段重复。底层思路见 [持久知识层](../概念/持久知识层.md)。

## 自动化负责记录，理解依靠证据

本地 llm-wiki skill 的 Update Chain 要求先搜索、合并同一对象，再同步入口与日志；Conflict Merge 要求比较范围与指标。nashsu 则展示了来源缓存、页面合并保护与结构检查的工程做法。见 [规范笔记](../../来源/SRC-LOCAL-SKILL/阅读笔记.md)、[固定版本源码笔记](../../来源/SRC-NASHSU/阅读笔记.md)。

来源版本、哈希、页面引用和目录适合由确定性工具维护。机制解释、证据可比性与冲突处理需要阅读实际内容。自动目录只负责找得到文章，结构检查通过也不提高科学证据等级；相关边界见 [证据与范围](../概念/证据与适用范围.md)。

为了减少日常维护，每篇论文保留一份主要精读笔记，问题页保存跨论文理解，目录从问题与论文关联自动生成。处理状态与收据留在元数据，正文专注技术；用户给论文后不必另外维护一套阶段任务表。执行细节见 [维护流程](../../维护/工作流.md)。

## 更新时避免两种误判

一种误判是来源哈希没变就无需再看。输出可能已经缺失，阅读要求或笔记也可能变化，需要结合处理记录判断；普通导航变更则不应触发全库重读。具体机制见 [增量摄入与失效传播](../概念/增量摄入与失效传播.md)。

另一种误判是成功合并了文件就保留了全部知识。来源数组可以完整，旧正文中的假设和边界仍可能丢失。因此，合并需要核对陈述及条件，保留无法判定的分歧，不能只看文件是否存在。

三份参考分别提供组织模式、维护约定和工程实现；这里的组合不依赖部署其桌面应用，也不采纳未经复测的性能数字。检索或存储是否需要扩展，应由实际漏查、规模和维护成本决定。
