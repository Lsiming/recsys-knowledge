# 上下文与多会话协作

本规范由 [AGENTS](../../AGENTS.md) 引用。采用可阅读的文件约定与本地 Git，不依赖聊天历史或远端服务；负责人登记不是程序锁。

## 1. 信息分层

| 层 | 文件 | 更新时机 |
|---|---|---|
| 执行规则 | 根 AGENTS、此规范、研究工作流 | 执行约定改变时 |
| 长期背景 | docs/PROJECT_BACKGROUND.md | 目标、业务定义或范围改变时 |
| 当前事实 | 根 PROJECT_MEMORY.md | 新结论有证据、旧决定被替代时 |
| 总交接 | 根 SESSION.md | 主线或关键任务状态改变时 |
| 任务注册 | 根 TODO.md | 认领、状态、负责人、完成条件改变时 |
| 独立交接 | docs/会话/<任务ID>.md | 本任务暂停、失败、交接、完成或恢复时 |
| 专题证据 | docs/研究/、docs/实验/ | 新资料、新实验、新分析时 |
| 历史原文 | docs/历史归档/ | 大幅压缩或替换有价值的上下文前 |

README 与索引只做路由；指标明细、逐轮日志和长篇解读不进入根上下文。一个稳定结论优先在所属专题详述，MEMORY 只写结论、限制和链接。

指令以用户最新有效要求为准；研究事实以版本匹配的原文、实际代码、配置和产物为证据。代码与论文不一致时记录差异，不擅自把实现写成论文定义；记忆与真实证据冲突时修正记忆并保留替代理由。

## 2. 注册与认领

1. 用 `CTX-001`、`R001`、`EXP-001` 等稳定唯一 ID 标识任务；重开同一问题继续原 ID，独立问题新建 ID。
2. 先检查 TODO 和所有相关任务交接，避免重复工作。由整合会话登记负责人、写入范围及完成条件；负责人使用会话名或可辨认的角色，不能只写“Agent”。
3. 并发任务在开始编辑前建立 `docs/会话/<任务ID>.md`。单个极短任务可复用总交接，但一旦出现并行就拆分。
4. 写入范围以明确文件或专题目录列出；共享文件只记录“待整合”，不把它们同时分配给多个会话。整合者变更时在 SESSION 和相关交接中写明。

状态使用：待明确、待认领、进行中、待整合、阻塞、已完成、已取消。阻塞记录具体依赖和已经完成的独立工作；完成需交付与适用验证已满足。TODO 仅保留有效任务，完成细节留独立交接。

## 3. 多会话如何工作

例如整合会话负责总路线和共享索引，R001 会话读序列建模论文，R002 会话读交易价值建模论文。各会话只写自己的专题与交接；完成后提交本地分支并注明待合并内容，整合者逐个审阅合并，再统一更新 MEMORY、SESSION、TODO 和索引。

这只是协作示例，不表示当前已有这些任务或会话，也不要求每项工作启动多个 Agent。

### 独立工作树：并行实质性修改优先使用

在已存在主线提交后，由整合者从确认的基线创建工作树。以下为示例任务 ID，实际执行时替换，并先检查目标路径不存在、分支未被占用：

```bash
git worktree list
git worktree add -b research/R001 ../推荐大模型-R001 main
```

把相应会话的工作目录设为新工作树；记录创建基线、分支和实际工作目录。工作树内按任务范围验证并做本地提交。它共享本地 Git 历史，但有独立工作文件与索引。

整合者在主工作树确认无未提交/暂存变更后串行合并：

```bash
git switch main
git merge --no-ff research/R001
python3 scripts/check_context.py
git diff --check
```

有其他未提交变更时先完成其所属任务或另建整合工作树，不自动 stash/reset。冲突逐文件核对最新事实和双方修改，验证后再完成合并；不整份选 ours/theirs 覆盖共享上下文。完成后检查 `git status`，合并结果及最新共享状态写入总交接。

### 共享一个工作目录

只允许文件范围互不重叠的编辑；Git 分支切换、暂存和提交由整合者串行操作。其他会话交付明确文件清单及待合并片段，不自行切分支或提交。两个会话都需要同一文件时，先拆到各自专题/交接，或指定唯一编辑者。

编辑前和写回前都重读共享文件及 diff；发现内容发生变化先合并。登记表不能消除同时写入竞态，无法确保串行时改用独立工作树。

## 4. 交接最少内容

使用 [任务交接模板](../模板/任务交接模板.md)：任务/负责人、分支/基线、写入范围、目标、已完成与证据、未提交文件、实际检查、阻塞、下一条可执行动作、待整合摘要。实验另写 run ID、真实输出和失败位置，禁止把“已提交运行”写成“实验成功”。

接手者先核对当前用户要求、Git 状态、TODO 和任务交接；再检查真实产物。日期旧不自动代表任务过期，历史未来时态不代表新授权。未提交文件以当前 diff 为准，不能凭交接清单删除或回退。

## 5. 精简与归档

常规小幅更新依靠 Git 保留历史，不机械每天复制整套文档。大幅替换、缩短有价值的长上下文时，先把修改前原字节保存到 `docs/历史归档/<YYYYMMDD_主题>/`，说明来源、替代文档和归档原因，再写新版本。并发增量先合并后决定归档来源。

归档不再表示当前状态；当前文件必须保留仍有效的限制和证据链接。禁止重新复制旧待办、旧停点或旧授权到当前文件而不核对。

## 6. 收尾

完成专题 → 验证 → 更新独立交接 → 提交任务分支/交付文件 → 整合者审阅合并 → 同步共享状态 → 检查与本地提交。单会话时这些角色由同一会话承担。

检查使用 [研究工作流](研究工作流.md) 的分级要求。检查器不验证实际会话是否在线、不自动锁定文件，也不自动创建或合并任务。
