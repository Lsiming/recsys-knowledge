# 三份参考资料的研究与适配

检索日期：2026-10-25。本文区分“原文提出”“源码可见”和“本仓库设计推断”；没有执行外部应用或其测试。本次将 nashsu 项目作为功能丰富的实践参考，未验证“GitHub 上最完整”这一比较性描述。

## 1. 本地 llm-wiki skill：把知识维护变成明确操作

本次读取的 skill 声明版本为 `4.0.0`，主文件位于 `~/.codex/skills/llm-wiki/SKILL.md`，并读取了 `AGENTS.md`、`index.md`、`SCHEMA.md`、`_meta/context-packs.md`、`_meta/update-policy.md`、`_meta/lint-policy.md`。哈希见 [来源清单](sources.json)。

它维护的是已有的团队业务 Wiki，覆盖金融风控等主题；其目录、字段和业务结论不属于本项目的推荐系统知识。

| 机制 | 原文件如何规定 | 对本仓库的启发 |
|---|---|---|
| 轻量定位 | 先读规则、全局索引和任务上下文包，再按关键词搜索 | 避免每次让 Agent 扫描所有论文和历史交接 |
| 知识归属 | 按概念、数据、特征、样本、模型、流程等语义对象组织 | 内容需要稳定归属，不能只按收集日期存放 |
| 建页阈值 | 多来源反复出现，或本身是重要任务/来源核心，才独立建页 | 防止一篇论文产生几十个无用页面 |
| 更新闭环 | 页面、索引、路由、别名、日志按影响同轮更新 | “能搜到、能接手”也是交付的一部分 |
| 冲突合并 | 比日期、权威性、作用范围和指标；不静默覆盖 | 同一结论在不同条件下可能同时成立 |
| 脚本沉淀 | 代码归档同步说明、环境参数和语义页入口 | 代码要连接到“解决什么问题、何时能用” |
| 长期记忆 | 沉淀稳定决策、已验证经验；排除临时进度和重复内容 | 会话历史与知识正文需要分开 |
| 最小原始证据 | 保存核心报告和必要汇总，不镜像整个实验现场 | Wiki 不承担大型模型或运行产物仓库职责 |

最值得借鉴的是“按任务选最少上下文”和“从 diff 反查更新义务”。这些措施比单纯堆目录更能维持日常可用性。

本地样本也显示了维护难点：`context-packs.md` 中存在重复 `updated` 字段，而且其启动文字仍包含“先读 Schema 和日志”，与较轻量的主 skill 启动顺序不同。它说明操作约定本身也会漂移，应该有单一主规则和可验证字段；本文没有修改该外部 Wiki。

需要适配的部分：

- 其 `git pull/push`、GitLab 同步、`git add -A` 不适用于本仓库；继续遵守本地 Git 和明确文件提交约定。
- 当前仓库 `PROJECT_MEMORY.md` 是项目状态与决定，不应逐步变成推荐知识百科。领域结论应进入专题知识页。
- “每页至少两个出链”和“约 200 行拆页”可作审阅提示。链接必须有关系含义，完整公式推导也不应仅因行数被拆碎。
- `confidence: high` 不能替代可定位证据。“作者报告”与“本地复现”需要逐项区分。
- 自动沉淀应服从当前任务范围。学习该 skill 不等于授权操作它管理的团队仓库或推送资料。

## 2. Karpathy：把知识编译为持久、可修改的中间层

原始来源：[Gist《llm-wiki.md》](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。本次通读的固定内容版本为 [6b0cef32 原文](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw/6b0cef32d73931fcab7498a7e82208e3ea41ee6f/llm-wiki.md)，内容 SHA256 见清单。

### 原文提出的架构

三层分别是不可变原始资料、持续更新的 Markdown Wiki，以及约束维护行为的 Schema。人负责资料选择、问题和方向，LLM 负责整理、连接和维护。原文把 Obsidian 比作阅读与浏览的工作界面，而非必需基础设施。

三个核心操作：

1. **Ingest**：读取一份新资料，产出来源理解，修改相关概念与主题，记录冲突，更新索引与日志。
2. **Query**：从已有知识中引用作答；有复用价值的比较、分析和新连接可以继续沉淀。
3. **Lint**：发现矛盾、过时观点、孤立页、缺失链接与知识缺口。

`index.md` 表示现在有什么，`log.md` 表示什么时候发生过什么，两者职责不同。原文称中等规模约百份来源、数百页面时，索引导航已可能足够；这属于作者经验描述，不是容量或性能保证。搜索引擎、向量检索和其他界面都是可选模块。

### 对推荐系统知识库的价值

论文阅读容易留下“一篇一篇摘要”，却没有持续更新“我们现在怎样理解序列建模或补贴决策”。持久 Wiki 可以把每次阅读变成对既有理解的修订，从而支持方法演进、反例、适用边界和问题导向的检索。

例如，连续阅读三篇候选生成式推荐论文时，应逐步改进“物品表示、训练目标、解码约束、评估协议”的比较，而不只是新增三个摘要。此处是工作流示例，没有在本轮开展这些论文的文献审查。

### 需要补足的研究纪律

- 原文“LLM 维护成本近乎为零”是设计愿景。科研材料仍有解析、引用核验、计算和审阅成本。
- 该模式强调与查询时重新拼接资料的差别；工程上仍可结合全文或语义检索，两者可以共同使用。
- Wiki 不应被视为无需回查的真相。数字、公式和争议结论需要原文定位，查询也应允许直接检索原始资料。
- 生成的综合不能再次作为独立证据计算。五篇相互转述同一实验的解读仍可能只有一个原始证据来源。
- 原文刻意保持抽象，不能据它推定必须采用某个目录、数据库或桌面应用。

## 3. nashsu/llm_wiki：把维护模式工程化

固定研究基线：`e08cfce65aad8b76b13546a081c1a8d4422b70c3`，提交日期 2026-10-21；该版本 `package.json` 声明 `0.6.13`。阅读入口：[固定版本中文 README](https://github.com/nashsu/llm_wiki/blob/e08cfce65aad8b76b13546a081c1a8d4422b70c3/README_CN.md)。

### 最有价值的工程机制

| 机制 | 阅读到的实现依据 | 对本仓库的取舍 |
|---|---|---|
| 目标与结构分离 | `templates.ts` 分别定义 purpose 和 schema | 使用现有项目背景承载目标；新增知识库规范承载结构，避免复制两份目的文档 |
| 分阶段摄入 | `ingest.ts` 先做结构化分析，再生成/合并页面，可附加审核与修复 | 先列出新信息和受影响页，再编辑；不必固定为恰好两次模型调用 |
| 建页与命名控制 | 分析提示要求独立建页理由、复用现有规范名 | 先搜索与识别同一概念，再决定新建；保存中英文别名 |
| 增量缓存 | `ingest-cache.ts` 用 SHA256 比较内容，并检查既有输出文件存在 | 后续工具加入来源、解析器、Schema、提示和模型版本的处理签名 |
| 保留旧贡献 | `page-merge.ts` 合并数组字段、锁定身份元数据、对正文合并做检查 | 知识页合并应保留来自不同来源的条件和证据 |
| 控制写入顺序 | `ingest-commit-coordinator.ts` 允许准备并行、落盘按预留顺序执行 | 借鉴准备与整合分离；本仓库仍遵守现有单整合者约定 |
| 程序维护汇总 | `ingest.ts` 对索引和概要有确定性增量更新 | 程序负责列表，Agent 负责领域理解，避免大模型反复重写大索引 |
| 维护分层 | `lint.ts` 与 `lint-structural-core.ts` 分结构检查和语义检查 | 链接/字段可脚本化，科研矛盾用模型辅助、人工判断 |
| 审核与未决项 | `sweep-reviews.ts` 保留需判断的矛盾等事项 | 页面生成可以继续，但待复核结论不能自动晋级 |
| 兼容 Agent | MCP README 明确工具调用运行中的桌面应用 API | 未来可接入；当前本地文件检索不需要依赖桌面服务 |

以上是静态阅读发现，不能据此声称应用在本机可用或已通过其测试。具体文件的固定链接与阅读范围见 [来源清单](sources.json)。

### 文档与源码需要分开核实

**索引与概要。** README 描述摄入时更新全局概要；当前 `ingest.ts` 的生成提示明确禁止模型生成 `wiki/index.md` 和 `wiki/overview.md`，改由程序增量维护。概要函数更新的是有上限的最近条目区，不能把它理解成每次重新完成全局研究综合。由此，本仓库应区分“自动目录/最近更新”和“人工审阅的领域综述”。

**合并失败。** `page-merge.ts` 做了旧元数据保护与正文检查，但某些失败分支会采用“新正文 + 数组并集”，并尽力备份旧页。保留 `sources[]` 并不保证旧知识正文仍完整；本仓库的核心知识页合并失败时更适合保留旧页、另存候选、登记待整合。

**删除来源。** 本次查看的 `deleteSourceFiles` 对多来源共享页移除来源字段并保留正文；这不是逐条撤销该来源独有结论。研究库必须再区分本地文件丢失、撤回资料、作者更正和知识失效，不能仅靠级联删链接解决。

**缓存。** 当前缓存比较来源内容及产物存在性；它没有在该缓存结构中编码整套处理协议版本。本仓库若以后调整解析方法、提示或证据规范，需要支持显式重新处理，不能因文件字节未变就永久跳过。

**检索与效果。** README 展示了可选向量搜索、图谱扩展和召回率数据。本轮没有复测，不将其数据作为本仓库选择工具的效果依据。源码 `search.ts` 已调用共享后端；较早的前端预算辅助模块与 README 的比例/单位也不能直接等同于当前完整 Agent 运行时。

### 建议吸收的顺序

先吸收来源身份、增量更新、合并保护、结构检查、审核队列；再考虑搜索与批量队列；图谱、社区发现、浏览器扩展、桌面 UI 和 MCP 放在真实使用需求出现之后。图谱连接强弱适合发现候选关联，无法证明两个方法等价或论文结论成立。

## 4. 三份参考在本仓库的组合

| 参考 | 主要贡献 | 本仓库进一步补足 |
|---|---|---|
| Karpathy | 持久综合层；Ingest / Query / Lint 的积累闭环 | 原文证据、研究状态、版本与实验边界 |
| 本地 skill | 轻量路由、知识归属、更新事务、长期记忆 | 推荐系统领域结构；简化团队同步；消除规范重复 |
| nashsu 项目 | 缓存、合并、队列、审核、检索和交互实现 | 关键结论的细粒度证据、更新失效传播、研究质量评估 |

因此建议以科研可追溯性为基础，以问题驱动知识生长，以可替换的 Markdown 文件为长期资产，再选择合适的运行工具。完整结构见 [知识结构与证据模型](02_知识结构与证据模型.md)，实施闭环见 [工作流与迭代路线](03_工作流与迭代路线.md)。
