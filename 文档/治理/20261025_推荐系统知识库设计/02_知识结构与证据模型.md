# 知识结构与证据模型

设计日期：2026-10-25；以下目录、字段与页面均为建议，示例不表示已经完成相应文献阅读或实现。

## 1. 四类内容与一套规则

| 内容 | 它回答的问题 | 应保留什么 |
|---|---|---|
| 原始资料与来源登记 | 我读的到底是哪份材料？ | 论文/代码/解读的独立身份、版本、原件与恢复位置 |
| 研究笔记 | 这份资料怎样推导、实现、验证？我理解到哪里？ | 单篇推导、关键证据、个人疑问、代码核对和局限 |
| 知识 Wiki | 跨多份资料后，我现在怎样理解这个问题？ | 定义、机制、方法关系、条件化结论、反例和研究缺口 |
| 应用与实验 | 这些理解能否解答问题、指导实现？ | 学习路径、专题回答、实验协议与真实结果 |

目标、结构、证据和维护规则贯穿四类内容。知识不是严格的一次性流水线：实验会修正概念页，新问题也会反过来要求重读原文。

主要正文保持唯一归属。来源卡只管材料身份和处理情况；研究笔记负责深读；Wiki 不再复制同一篇论文的完整摘要，而是抽取能跨论文复用的知识。

## 2. 从现有仓库平滑演进

下面展示成熟后的职责布局。首轮只建立用得上的部分，不预先生成所有空目录或空知识页。

```text
推荐大模型/
├── README.md                       人类入口与当前知识地图
├── AGENTS.md                       Agent 执行规则
├── PROJECT_MEMORY.md               当前项目事实与决定
├── SESSION.md / TODO.md             交接 / 唯一任务注册表
├── sources/                        轻量来源卡：身份、版本、位置、处理状态
├── papers/                         原始 PDF，沿用当前忽略约定
├── raw/                            其他原始材料；大文件与本地剪藏不入 Git
├── wiki/
│   ├── index.md                    短导航；完整列表以后由程序生成
│   ├── 领域/                      三个领域的知识地图与边界
│   ├── 概念/                      可跨领域复用的定义与原理
│   ├── 专题/                      问题驱动的比较、综述和演进
│   ├── 问题/                      持续值得研究的未决问题
│   ├── 方法/                      方法族、模型机制，按需要扩展
│   ├── 评估/                      指标与评估协议，按需要扩展
│   └── 学习路径/                  先修关系、练习和复习入口，按需要扩展
├── docs/
│   ├── PROJECT_BACKGROUND.md       唯一长期目标入口，承担 purpose 职责
│   ├── 规范/知识库规范.md          未来唯一知识 Schema；引用现有研究/协作规则
│   ├── 研究/<主题>/               保留单篇笔记、推导与代码阅读记录
│   ├── 实验/<实验ID>/             保留实验协议、结果和局限
│   ├── 治理/ / 会话/ / 模板/      继续沿用现有职责
├── code/                           自己维护的教学示例与小型实现
├── reproductions/<实验ID>/         实验入口、配置、补丁与依赖声明
├── scripts/                        入库、索引、lint 等维护工具
└── .local/                         上游源码快照、解析缓存、搜索索引等可再生内容
```

首轮建议只新增 `sources/`、`wiki/index.md`、必要的领域/概念/专题/问题页面及一份知识库规范。现有 `docs/研究/`、`docs/实验/` 和会话约定继续使用；无需为了目录整齐而整体迁移。

素材存储有两种合理选择：沿用本地 `papers/` 与 `raw/`，或让 Zotero 等文献管理器保管 PDF、仓库只登记身份与本地位置。只能选一个原件管理主入口，不能两边独立改版本。工具偏好确定前，来源身份与笔记格式应同时兼容这两种选择。

Git 保存来源元数据、笔记、知识、代码、配置和小型汇总。PDF、上游完整源码、样本、权重和解析缓存需单独备份或可恢复。现有 `.gitignore` 尚未覆盖未来所有新目录，实施阶段必须逐项核对，不能认为写入示意目录就会自动忽略。

## 3. 三个领域入口，共享知识基础

领域目录用来浏览，不把全部正文按领域复制。以下是待建设的知识地图，并非本轮已经核实的文献结论。

| 领域入口 | 需要组织的核心问题 | 可能形成的方法/机制专题 |
|---|---|---|
| 传统推荐 | 如何匹配用户与物品；如何预测反馈；如何组合多目标；怎样兼顾效果与服务成本 | 协同过滤与矩阵分解、召回/排序/重排、特征交互、双塔、序列与图建模、多任务学习、探索利用 |
| 营销补贴 | 给谁、给什么、给多少、何时给；在预算和长期价值约束下怎样决策 | 响应预测、uplift/CATE、多处理/连续处理、策略学习、离线策略评估、预算分配、bandit/RL、长期价值 |
| 生成式推荐 | 生成什么；物品如何表示；训练与推理怎样对应；如何服务真实候选空间 | 语义 ID/离散化、生成式检索、序列生成、LLM 推荐、约束解码、候选更新、推理效率与评估 |

每个入口按同一骨架组织：任务与对象 → 必要基础 → 方法族 → 代表资料与代码 → 评估 → 未解决问题。将“已建立页面”“待补知识”分开标明，空白用地图条目表示，不写成貌似完整的教程。

共享基础建议覆盖概率统计与优化、表示学习、序列建模、采样与偏差、因果识别、实验设计、指标与服务约束。只在当前资料需要时逐步补页，不先生成整本机器学习教材。

跨领域连接要解释关系及差异。例如“预测转化”可以关联“增量转化”，但前者的预测精度无法直接证明后者的处理效果；生成式检索的离线命中也不能直接替代在线商业收益。这些是评估边界，具体方法优劣仍需资料和实验。

## 4. 按对象存，按多个维度看

一篇资料可能同时涉及生成式推荐、序列建模和离散表示；一份因果评估方法也可能被多个业务问题引用。只保留一份来源记录和主要笔记，利用领域入口、标签与正文链接形成多个视图。

建议核心页面类型与职责：

| 页面类型 | 关键内容 | 建页时机 |
|---|---|---|
| 来源卡 | 题名、作者、URL/标识、版本、文件位置、笔记入口 | 决定保存或处理一份真实资料时 |
| 单篇笔记 | 问题、方法、推导、证据、代码差异、疑问 | 真正开始阅读/分析时，不给每份收藏强制写长摘要 |
| 概念页 | 明确定义、符号、直觉、适用条件、例子、相关概念 | 核心概念或反复出现、值得复用时 |
| 方法页 | 输入输出、目标、训练/推理、关键假设、成本、失败情形 | 方法本身值得独立比较，不等同于一篇论文时 |
| 评估页 | 指标定义、协议、可比条件、偏差、常见误用 | 当前问题需要反复引用时 |
| 专题页 | 问题边界、方法比较、演进关系、条件化结论和反例 | 多资料围绕一个明确问题形成综合时 |
| 问题页 | 可回答的问题、已有认识、缺失证据、相关资料 | 值得持续研究，而非一次性聊天疑问时 |
| 学习路径 | 先修关系、必读与选读、练习和自检 | 有足够真实内容可导航时 |

来源卡使用 `src-...` 稳定 ID；知识页使用 `kb-...`；任务继续用 `R001` 等；实验继续用 `EXP-...`。不同对象不要共用一个递增编号。名称可以调整，身份不随日期、目录和翻译变化。

同一论文的 arXiv、会议版、中文译文应建立作品关联；译文是派生资料，不能当作额外独立证据。官方代码仓库作为独立来源，与论文相互链接，并固定 commit。只读了某篇论文中的引用，不等于读过被引用论文，不为它伪造“全文已读”条目。

中文标题帮助阅读，`aliases` 保存英文术语、缩写和常用译名。早期每页自己的别名字段作为事实来源，遇到命名冲突再建立少量人工裁决；以后可以生成别名索引，避免两份手工词典漂移。

## 5. 用最少字段支撑追溯

不要一开始建设大型知识图谱数据库。先用 Markdown frontmatter + 正文中的证据表；只有反复出现的查询或检查需求才增加字段。

知识页头部示例：

```yaml
---
id: kb-example-budgeted-treatment
title: 预算约束下的处理分配
type: concept
domains: [marketing-subsidy]
aliases: [budgeted treatment allocation]
sources: [src-example-paper]
created: 2026-10-25
updated: 2026-10-25
review_status: draft
---
```

其中 `sources` 表示该页用到的来源，并不自动表示每句话都得到这些来源支持。每个重要数字、公式、优劣判断或迁移判断，需要在相邻正文或小表里标明：

| 字段 | 需要记录的内容 |
|---|---|
| 结论身份 | 必要时用页内 C01 等标识，便于其他页引用；不要求每句话独立建文件 |
| 证据类型 | 作者报告 / 本仓库复现 / 分析推断 / 待验证假设 |
| 定位 | 来源 ID、准确版本、章节/页码/公式/图表；代码用 commit + 文件/函数 |
| 作用范围 | 任务、人群、数据、时间、训练与评估协议、基准、资源 |
| 限制与反证 | 未排除的因素、相反证据、尚未验证的迁移条件 |

同页可以混合四类证据，因此不建议给整页只打一个“已复现”或“高置信度”标签。对通用定义也可在章节统一引用，不必逐句添加机械脚注。

来源卡至少记录 `id`、资料类型、原始 URL/DOI/arXiv、版本、取得日期、本地原件位置或恢复入口、内容哈希、阅读笔记链接。机器绝对路径放忽略的本地映射；共享元数据优先相对位置和稳定标识。

应把三个维度分开：

- **资料处理状态**：已登记、已解析、已整合、处理阻塞，放来源卡；已整合不代表全文精读。
- **阅读深度**：仅元信息/摘要、选读章节、全文已读，放研究笔记；必要时分别记录 Agent 和个人阅读情况。
- **知识复核状态**：草稿、已复核、待复核、已弃用，放知识页；实验是否成功放实验记录。

来源有多个版本时保存版本列表与各自哈希，知识证据指向实际使用的版本。正式发表、预印本更正和代码修订不能被一个模糊的“最新”字段覆盖。

## 6. 对推荐与补贴研究特别重要的证据约束

| 资料中的结果类型 | 进入知识页时必须带上的条件 |
|---|---|
| 推荐离线效果 | 任务、数据版本、切分方式、全量/采样候选、负采样、去重与过滤、指标 K、基线与调参预算 |
| 模型效率 | 参数、训练数据量、硬件、批大小、延迟测量口径、吞吐、索引/候选成本；缺失则标缺失 |
| 补贴增量效果 | 处理与对照、随机化或识别假设、倾向性/重叠、成本定义、预算、干扰与长期影响 |
| 策略价值 | 数据收集策略、可识别条件、离线估计协议、方差与支持范围、是否真实在线实验 |
| 生成式推荐 | ID/表示构造、词表与物品版本、训练目标、解码方式、候选约束、冷启动与更新、延迟和评估协议 |

信息不全时保留可核实部分并列出缺口，不填入“常见设置”冒充作者设置。来自不同协议的数字可并列呈现背景，但不能直接排出总体优劣。

## 7. 链接表示关系，图谱帮助导航

正文应解释链接为什么存在：需要某概念作为先修、某方法扩展了另一方法、某证据支持或反驳了结论、某实验验证了一个假设。仅有“相关链接”列表不容易形成体系。

第一阶段继续用标准 Markdown 相对链接，与现有检查器兼容，也能被 Obsidian 阅读。暂不同时维护两种链接作为正文主格式；若以后需要 `[[wikilinks]]`，先加入解析、重命名与断链检查，再迁移。不能把目前的 `check_context.py` 说成已经检查 wikilinks。

领域页、专题页和学习路径承担不同导航职责：领域页展示版图，专题页回答一个问题，学习路径表达先修与练习。全局索引只做入口，不能无限膨胀为“必须每次整本读取”的总目录。

## 8. 源码、实验与大型素材

自己维护的示例和研究实现可进 Git；上游完整代码优先放已忽略的 `.local/upstream/<项目>/<commit>/`，用只读快照和固定链接定位，不把多个带嵌套 Git 的项目直接塞入主仓库。小型必要补丁、启动入口、环境声明和许可证说明由复现实验保存。

代码笔记应连接“论文模块/公式 → 实际文件与函数 → 输入输出 → 与论文差异 → 对应实验”。没运行只标静态阅读，源码能打开不等于复现成功；日志和模型产物仍按现有约定留在忽略目录。

PDF 解析结果属于派生缓存，需记来源哈希、解析器与版本。复杂公式、表格和图不能仅凭文本提取判断；必要时回看原页并保存少量确有价值的裁图。局部重解析生成新的派生版本，不改写原 PDF。

原件、笔记和结论应能互相找到。纯本地 Git 不覆盖被忽略的素材，也不是磁盘故障备份；落地时选择用户已有备份位置，分别保护 Git 仓库、不可再取得的原件和必要实验汇总，并实际演练恢复。向量库、全文索引与普通解析缓存应可重建。

## 9. 什么叫“已经形成体系”

能沿一条路径完成“理解问题 → 找到概念与先修 → 比较方法 → 回查证据 → 识别边界 → 设计验证”，且能说清缺少什么。目录齐全、链接密集或长篇总结都不足以单独证明体系已形成。

例如对“某类生成式方法是否适合当前召回任务”应能定位方法机制、数据与候选条件、成本、评估协议和尚缺的实验；对“补贴应发给高响应者还是高增量者”应能区分预测对象、因果识别和预算目标。本轮只提出这种验收方式，没有给出具体业务决策结论。
